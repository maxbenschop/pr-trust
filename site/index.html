Let in the contributors you already trust.

How it works

One check, the moment a pull request opens

Rules are checked in order and the first match decides. Maintainers with write access and bots are never checked.

  1. 1

    A PR opens

    The workflow runs on pull_request_target with your repo's own token. It never checks out or runs the PR's code.

  2. 2

    Rules load from your default branch

    A pull request can't edit the rules that judge it. No rules file? Sensible defaults apply.

  3. 3

    The author is checked

    Against your Vouch list, lists from projects you trust, and merged work in repos you name. It checks the account that opened the PR, not the commit author, which anyone can fake.

  4. 4

    The PR gets a label

    admitted unknown denounced, with the reason in the job summary.

  5. 5

    Optionally: comment and close

    Unknown authors get your message and, if you choose, a closed PR. A maintainer reopening it always wins.

The order of checks

  1. denounced Denounced in your own list. Blocked, even for docs-only changes.
  2. admitted Vouched in your own list.
  3. admitted Matches one of your admit rules, in order.
  4. exempt Only touches paths you exempted, such as docs/**.
  5. unknown Nothing matched.

Install

Two files, then commit

No sign-up, no app to install. Add these to your default branch and the next outside PR gets checked.

1 Add your rules: .github/trust.yml

Start with labels only. You can switch to closing PRs once the labels look right.

own_list: auto                    # your VOUCHED.td, if you have one
admit:
  - list: ghostty-org/ghostty     # people a project you trust vouched for
  - merged: { repo: self, min: 1, within: 24mo }   # merged here before
on_unknown: label                 # label first; switch to close later

2 Add the workflow: .github/workflows/pr-trust.yml

Pinned to a release commit, so the code you run can never change under you.

3 Commit both files to your default branch

That's it. Open the Actions tab on the next outside PR to see the decision and the reason.

Roll it out safely

  1. Preview on your history. See what your rules would have done to the past year of PRs: 
    npx github:maxbenschop/pr-trust backtest your-org/your-repo --config .github/trust.yml
  2. Label for a few weeks with on_unknown: label. Nothing gets closed.
  3. Tune the rules if good people keep landing in "unknown". Try new rules on any PR first with npx github:maxbenschop/pr-trust check owner/repo#123 --config new.yml.
  4. Switch to closing with on_unknown: close and your own message_file.

Backtest

What the default rules would have done

We replayed a year of real pull requests (Nov 2025 – Nov 2026) in ten projects against the defaults: "vouched in your own list, or one earlier merged PR here". Each PR is judged with only what was known the day it opened.

Repository Outside PRs Keeps Stops Merged when let through Merged when blocked

The gate works

In every project, PRs it let through were merged more often than PRs it blocked, and it would have stopped 45–96% of the PRs maintainers rejected.

Newcomers pay the price

A first PR always fails "merged here before". In most projects, half or more of the outside PRs that later got merged would have been blocked.

Shared trust is the fix

That's why pr-trust can admit people vouched for by projects you trust, or with a track record elsewhere. Run the backtest with your own rules to see the difference.

Safety

Built for a write token on untrusted PRs

Never runs PR code

Everything happens through GitHub's API. Nothing from the pull request is checked out, built or executed.

Rules from the default branch

A pull request can't edit the policy that judges it.

Errors never close

If the check fails, the PR stays open with a "check failed" label for a maintainer.

Only your denouncements

Other projects can vouch for people in your repo, but never block them. Trust goes one step deep.

No server, no data

It runs inside your Actions with your token and talks only to GitHub.

Verifiable releases

The bundle is rebuilt in CI and must match the source. Releases carry a signed build attestation.

FAQ

Questions

How is this different from Vouch?

Vouch is a list and a check for one project. pr-trust reads Vouch lists, and adds what a single list can't: trusting other projects' lists, admitting people with a track record in repos you choose, docs-only exemptions, and a backtest to see the effect first. It runs alongside Vouch, so you can keep your setup.

Doesn't this shut out newcomers?

Any gate does, which is why the default is to label rather than close, and why the backtest shows exactly who would have been affected. Shared lists and track-record rules let in people who are new to your project but not new to open source. Your message tells everyone else how to get vouched.

Does it detect AI-written code?

No. It doesn't read the PR's content at all. It asks one question that can be answered reliably: has someone you trust vouched for this person, or have they done good work you can verify?

What does it cost?

Nothing. It's open source (Apache-2.0) and runs in your repo's GitHub Actions, typically in a few seconds with a handful of API calls per PR.

Why can't I use a merged rule for every project?

Merged rules use GitHub search. Some projects aren't in GitHub's search index (facebook/react), or land changes outside the merge button (golang/go, pytorch/pytorch), so their history can't be counted. The Action warns when a rule can't be checked.

What permissions does it need?

contents: read and pull-requests: write, the same as Vouch. See SECURITY.md for exactly what it does with them.
