Label pull requests by whether you trust the author.

pr-trust is a GitHub Action. It checks who opened each pull request against your own Vouch list, lists from projects you trust, and their merged work, then adds one of three labels. You know who you are dealing with before you open the diff.

Two files and a commit.

Add the rules file and the workflow, commit them to your default branch, and the next pull request gets a label. No app to authorise, no server to run. Skip the rules file and the defaults below apply.

Is the write token safe?

This is everything it asks for. It can label, comment on and close pull requests. It cannot push code.

permissions:
pull-requests: write
contents: read

It never runs pull request code.

The job runs from your default branch and never checks out the fork, so nothing an author writes is executed with your token.

A pull request cannot change the rules that judge it.

trust.yml and your list are always read from the default branch. Editing them in a pull request changes nothing until you merge it.

A failed check never closes anything.

If a list cannot be fetched or the run errors, the pull request stays open and gets a trust: check failed label, so a maintainer knows to look.

There is no server.

Everything happens inside GitHub Actions with the token GitHub issues for that one run. It talks to the GitHub API and nothing else.

Only your own list can block anyone.

Shared lists from other projects can vouch for people in your repo, but a denouncement only counts when it is in your own VOUCHED.td.

A maintainer reopening always wins.

If someone other than the author reopens a closed pull request, the check only labels it and never closes it again.

What about newcomers, and other doubts

Doesn't this shut out newcomers?

Out of the box, no. A newcomer's pull request is labelled unknown and stays open for you to review like any other. If you switch on closing, then yes, newcomers are blocked until someone vouches for them. That cost is real, and shared lists are the answer to it: a person vouched on a project you trust is vouched on yours from day one. Every unknown author also gets a comment linking to a page that explains how to get vouched.

What if someone I vouched for turns out to be a problem?

Remove their line from VOUCHED.td, or put a minus in front of it (-github:username) to denounce them. Your own list is checked before anything else, and a denouncement there wins.

Who controls a shared list?

The project that owns it. You decide which lists to accept in trust.yml and can drop one at any time. A shared list can only vouch for people in your repo, never denounce them.

Does my own team get labelled?

No. Anyone with write access to the repository is skipped, and so is every bot account, such as Dependabot and Renovate.

Can I try it without changing anything?

Yes. npx github:maxbenschop/pr-trust check owner/repo#123 shows what your rules would do to one pull request, and backtest replays a whole year. Both only read. They need Node 22.18 or later and a GitHub login (gh auth login). The Action also has a dry-run input that logs what it would do.

Do I need Vouch?

No. pr-trust reads VOUCHED.td files in the Vouch format, but works without one using merged-work rules. If you already use Vouch's own Action, the two can run side by side; there is an example workflow.

Can I change the labels or the comment?

Yes. labels: renames any of the four labels, message_file: points at your own comment text, and comment: never turns comments off. See the configuration reference.

Does it read the code to guess whether it is AI-written?

No. It looks at the author, and at file paths only if you set exempt paths. The label says who opened the pull request, not whether the change is any good.
